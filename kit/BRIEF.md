# Track 1 — AI Task Factory

**How can we automatically create realistic software-development tasks that are clear, solvable, and
reliably testable?**

Using a supplied working software repository and the [Harbor task interface](https://www.harborframework.com/),
your team will build **one reusable strategy** (a pipeline) for generating realistic feature-development
tasks suitable for evaluating AI coding systems.

Each generated **task package** must contain:
- clear, achievable **requirements** (a spec a competent engineer could implement from alone),
- a **reference implementation** (the "gold" solution), and
- **tests** that verify the new feature *and* protect existing functionality.

Packages must **identify their starting repository version** (a real `base_commit`) and **follow the supplied
task interface** exactly. Reference implementations and tests must work with the repository's language,
framework, dependencies, and execution environment.

---

## What "good" means here

A task is good when all three are true, and you have **evidence** for each:

1. **Fair / solvable** — the requirements are complete and unambiguous. Everything a hidden test depends on
   is stated in the spec; nothing requires guessing an undocumented constant, symbol, or convention. The
   reference implementation satisfies the requirements and the grader scores it **1.0**.
2. **Discriminating** — the feature tests actually *detect* missing or incorrect behavior: with no
   implementation (the base repo), the feature tests **fail**.
3. **Regression-safe** — existing behavior is protected: a curated set of pre-existing tests still **passes**
   both at the base repo and under the reference implementation.

> The validation protocol in `docs/validation_protocol.md` turns these three into mechanical checks you run
> with the harness. A package that doesn't produce all three green is not done.

**Tests verify observable outcomes, not a specific implementation.** Your tests must assert the behavior and
compatibility the spec states — never a particular algorithm, structure, or internal helper. **Any
implementation that satisfies the requirements is accepted**; evaluation compares a solver's behavior to the
spec, not its code to your reference solution.

## How your submission is assessed

We assess, across the packages your pipeline produces: **reliability** (fraction that are valid, unedited),
**fairness** (spec-complete, implementable blind), **difficulty** (the benchmark model struggles),
**meaningful variation**, **regression protection**, **reproducibility**, and **efficiency** (cost per valid
task). **Difficulty, novelty against live upstream, and efficiency do affect the result** — they are not
decorative. The full rubric and its weights are published (see below); only the internal gate thresholds and
the LLM-judge mechanism are not.

The **full judging rubric** — seven weighted dimensions (Reliability 20 · Fairness 15 · Hardness 20 · Variation 20 · Regression 10 · Reproducibility 5 · Efficiency 10 = 100), the validation gates, the floor, and
the tie-break — is in `JUDGING.md`.

## Produce 5 distinct tasks from your chosen repo

Your pipeline must produce **5 distinct tasks** from a single supplied repository — it is a *factory*, not a
one-shot generator. The 5 tasks must differ **substantively** — in behavior, rules, state
transitions, or interactions — not by rewording or renaming. Your pipeline's value is its **strategy for
creating variation**, and you must be able to explain *how* it does so. Five reworded variants are worth
far less than five that each exercise a genuinely different capability of the repository.

*Example (illustrative only):* a shopping-cart app might get a generated task to add discount codes with
eligibility rules and spending thresholds. That shows the *kind* of work — not the repository you'll use.

**novel against live upstream** (the capability isn't already shipped, including in PRs merged *after* your
base commit, and isn't a drop-in from a well-known library).

## Your deliverable

1. **A task-generation pipeline** — code (and model-API calls, if you use them) that produces task packages in
   the Harbor interface — **5 distinct tasks from your chosen supplied repository**.
2. **The 5 task packages** — generated by the pipeline, each well-formed and mechanically sound.
3. **Validation evidence** — self-check output showing, per package: gold scores 1.0, feature tests fail
   without the implementation, and the regression set stays green.
4. **A variation writeup** — a short explanation of how your strategy creates *meaningful* variation across
   the tasks it generates from one repository.

Demonstrate the pipeline generating **and** self-checking packages end to end.

See `SUBMISSION.md` for exactly what to hand back, `docs/harbor_task_interface.md` for the package format,
`docs/validation_protocol.md` + `harness/` for the self-check, and `benchmark/` for the finish line: running a
the benchmark model against your tasks. How you design the pipeline is up to you — that is what we are evaluating.

## Rules

- **Teams** of 5 participants; all members participate in person.
- **Build time:** 4 hours 30 minutes for the core solution. Presentations and judging are outside the build
  window. Submit the state of your work by the deadline.
- **Allowed tools:** AI coding assistants, model APIs, open-source libraries, and general-purpose utilities,
  subject to the access and budget rules. **Disclose pre-existing code and reused components.**
- **Teamwork:** work within your team; organizer guidance is fine, but people outside the team must not build
  your submission.
- **Access and budget:** use the organizer-provided keys within the allocated budgets. Personal paid accounts
  and additional API spend are not allowed.
- **Transparency:** clearly identify manual interventions, incomplete functionality, and limitations; your demo
  and reported results must reflect the submitted work.
- **Partial completion:** incomplete submissions are accepted, receive credit for the work demonstrated, and
  are eligible for prizes under the same rubric. Clearly distinguish working components from planned/incomplete
  ones.
